# Decisions log

## Specimen rack rebuild (superseding the earlier "neon glass" iteration)

- A new build-plan prompt arrived mid-project with a completely different visual identity (monochrome lab/specimen-rack, test tubes) and explicitly re-states a minimal, closed feature list ("only these features, nothing more", "do not add priorities", "strictly monochrome, zero hue anywhere"). Treating this as a full replacement of the prior session's ad-hoc additions — the 5-theme color switcher, the `urgent` flag, and the free-text notes editor — since all three directly contradict this spec's explicit constraints (color at all; "no priorities"; "only these features"). If the user wants any of those back later, they're one ask away — the backend data those features touched isn't destroyed (see below), just no longer surfaced.
- Did NOT run a destructive migration to drop the `urgent`/`notes` columns from the existing `/data/queue.db` — SQLite `DROP COLUMN` support varies by build and a table-rebuild migration is unnecessary risk for zero benefit. The columns stay in the schema, now unused and un-serialized by the API; the 5 real tasks already in the database keep their `title`/`tag`/`state`/timestamps/`position` exactly as-is. Only their `urgent`/notes values stop being exposed, which is consistent with the new spec dropping those concepts entirely.
- Removed the theme switcher UI and `src/themes.ts` entirely rather than leaving it disabled/dead — the new spec is explicit that color must be zero, so a hidden color-picker would be actively wrong to leave reachable.
- Kept the core state machine (arm→confirm start, forced-pause-before-switching, pause-note-required, resume-reveal-then-flip, done/drop exit) unchanged — none of that logic is visual, and the new spec's feature list (add/start/pause/resume/done/drop, single active task, forced pause when switching) is functionally identical to what was already built and tested. Re-skinned the components around it rather than rewriting the interaction logic from scratch.
- Liquid rendering: used layered CSS gradients for the meniscus/sheen instead of a true `feTurbulence`/`feDisplacementMap` SVG refraction pipeline — the spec allows "canvas only if SVG can't hit 60fps," and a full per-frame turbulence filter on every visible tube risked exactly that on a 12+ tube rack; the layered-gradient approach reads as convincing glass/liquid at a fraction of the paint cost.
- Tag encoding without color, per spec: `work` = solid liquid fill + flat round stopper; `study` = halftone dot-pattern fill + domed stopper; `task` = diagonal hatch-pattern fill + ribbed screw cap.
- Shatter-on-drop implemented as a fixed set of pre-defined polygon shard pieces (clip-path) with per-shard randomized (but seeded) velocity/rotation, rather than a physics-simulated fracture — visually reads as "shatters," avoids a physics engine dependency for one animation.
- The scramble-text reveal on Add decodes each character from a random glyph pool over a few frames using `requestAnimationFrame`, not a library — keeps the bundle free of a text-animation dependency for a single use.
- Fonts: Space Mono (UI/labels) + Reenie Beanie (handwritten note) per spec, replacing Bricolage Grotesque/Space Grotesk/Caveat from the prior theme.

## Label legibility fix + per-tube monochrome variety

- Real titles (15-20+ chars) were unreadable — the label was a single `nowrap` line with ellipsis, truncating after ~4 characters ("desi…"). Fixed by: widening tubes (rack 108→140px, bench 200→215px), switching the title to a `-webkit-line-clamp: 4` wrapped block instead of single-line truncation, and auto-shrinking the title font by character count (5 size tiers from 0.7em down to 0.44em) so even a 30-character title fits without losing words. Also switched the label background from a translucent tint to a fully opaque one (`var(--bg)`) — the original translucent label had almost no contrast against the dot/hatch liquid patterns behind it, making text unreadable even before the truncation bug.
- Added 30 discrete per-tube "variants" (`tubeVariant()` in `utils/tube.ts`), seeded by id so they're stable: each varies liquid glow intensity/blur, an outer halo glow on the glass, a diagonal liquid sheen at its own angle/strength, a faint low-saturation hue tint on the glow/halo/label edge only, and the density/scale of the dot or hatch pattern. This makes every tube read as a visual individual — in how the liquid itself looks, not just its glow — without touching the tag-encoded pattern type or cap shape, which must stay fixed for the pattern+cap-equals-tag meaning to hold. The hue never touches the body/liquid/cap itself, so the piece still reads as monochrome overall.

## Mandatory per-task deadline estimate, queue-cumulative scheduling, dustbin, and extend

- Mapped the request directly onto the existing metaphor instead of inventing new UI: liquid level *is* the countdown. Every new tube requires an upper-bound day estimate (1-30) at creation — this isn't optional, since the whole scheduling model depends on every tube actually carrying a number.
- The rack is a **shared timeline, not independent deadlines**: a tube's displayed remaining time is its own estimate *plus* every timed tube ahead of it in queue order (`computeCumulativeMs()` in `utils/tube.ts`). This is a pure display-layer computation recomputed fresh from live state on every tick — each task's own `expiresAt` is completely independent and never mutated by its neighbors — which is what makes three different user asks fall out for free with zero special-casing:
  - finishing a task early removes its term from the running sum immediately, so everything behind it shows a shorter wait the instant it happens
  - dragging a tube to a new rack position changes who's "ahead" of it, so the sums (and each tube's liquid level) recompute on their own
  - extending a task's own estimate (see below) lengthens everything behind it automatically, since the sum just includes a bigger term for that task
- A full tube now represents 30 days (`MAX_DAYS`) of *queue* time, not a single task's own setting — this fixes a real bug where every fresh tube looked almost equally full regardless of whether it was given 2 days or 10, because fill was originally relative to the task's own total. Fill is now relative to the fixed 30-day scale, so a 3-day task visibly shows far less full than a 25-day one, and a backlog of several queued tasks can fill a tube on its own even if no single task is long.
- Countdown ticks every 1 second (explicit ask) via the app's periodic re-render; the `.liquid` height's existing CSS transition smooths between ticks so it reads as continuous draining rather than stepping.
- On expiry: client catches the moment during an open session and plays a "tipped into the dustbin" flight animation (gentle — no shatter; shattering reads as punitive/destructive, and expiry must never feel like data loss). The server also lazily sweeps expired `queued`/`paused` rows on every `GET /api/tasks`, so correctness holds even if the tab was closed when the countdown actually hit zero — nothing is ever silently gone, it's always sitting in the dustbin.
- Dustbin is a separate, new, interactive component from the spec's existing `Drain` (which stays purely decorative for manual drops) — reusing it would have conflated "manually discarded" with "recoverable, just expired," two different meanings.
- Restore and extend both reuse the same `DaySlider` control as the add form (shared component) rather than bespoke UI — one mental model for "how many days" everywhere it appears. Extend is additive (`days_total += N`, `expires_at += N days`) rather than replacing the estimate outright, so a tube's original estimate and how much it's since been extended both stay visible in the data, and the new total immediately flows through the cumulative math for everything queued behind it.
- Schema: adding the `'expired'` state required rebuilding the `tasks` table, not just `ALTER TABLE ADD COLUMN` — SQLite's `CHECK` constraint is baked into the table definition at creation time and can't be altered in place. `migrate()` detects this (checking `sqlite_master.sql` for the literal `'expired'`) and only then does a rename-recreate-copy-drop rebuild, copying every column that actually exists so it's safe regardless of this database's migration history. Verified against the live database (real user tasks already in the rack) — all survived with the new `days_total`/`expires_at`/`expired_at` columns added, and all subsequent testing was done against throwaway tasks created and dropped specifically for verification, never touching the user's real queue.
