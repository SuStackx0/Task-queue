# Decisions log

- Frontend: Vite + React + TypeScript, `motion` (framer-motion) for springs/layout, `@use-gesture/react` for drag, CSS modules. Matches spec exactly.
- Backend: Fastify + better-sqlite3 in plain JS (not TS) — spec says backend is deliberately trivial, so skip the TS build step for the server and run it directly with Node.
- Single Node process serves API + static built frontend from `dist/`, matching "single Node process" requirement.
- SQLite file at `/data/queue.db` inside the container, volume-mounted to `./data` on the host.
- `state` enum as TEXT with a CHECK constraint; single-active-task enforced via a partial unique index `idx_one_active ON tasks(state) WHERE state = 'active'`.
- `position` is a float (fractional indexing) so reordering/inserting doesn't require rewriting every row; new tasks get `position = max(position) + 1`.
- IDs: integer autoincrement primary key from SQLite, simplest option, matches `id` in the schema.
- Ticket seeded rotation: derive a deterministic pseudo-random angle from the ticket's `id` (simple hash → range -3deg..3deg) so it's stable across renders/reloads.
- Aging: computed client-side from `created_at`/`paused_at` (whichever is more recent "hang" start) — no cron/job needed, purely a function of elapsed time at render.
- "hung Nd ago" clock for queued/paused tickets starts at `created_at` for never-started tasks, and at `paused_at` for paused tasks (that's when they went back on the rail).
- Reorder (drag along rail) only applies to queued/paused tickets, not the active one (it isn't on the rail) — PATCH position updates the float position value.
- Resume flow: ticket animates down already showing the back (note) for ~1.5s or until clicked, then flips to front and becomes active — implemented as a local UI state machine, no new API beyond `/resume`.
- "Start while busy": the UI auto-opens the pause-note flip for the currently active task; only on successful pause does it call `/start` for the newly chosen task. No separate backend endpoint needed — just UI sequencing.
- Used thermal-printer "slot" fixed at top-left of the rail bar itself (not a separate floating element) to keep the rail metaphor intact.
- Light/dark mode: follows `prefers-color-scheme`, with tokens as CSS custom properties on `:root`, no manual toggle (not in feature list, so skip extra UI for it — spec only asks it be reviewable in both via screenshots).
- Dropped tickets are deleted immediately on crumple-animation completion (optimistic UI + DELETE-like POST /drop), no undo (not in feature list).
- Keyboard nav operates on a single "focused ticket" index across the rail (active ticket excluded, since it's not on the rail); arrow keys move focus, not reorder, per spec table (`←/→ move along the rail` = move focus along the rail, not drag-reorder).
- better-sqlite3 chosen for sync, zero-dependency-hassle API matching "trivial backend" intent.
- Major visual pivot requested mid-build: dropped the paper kitchen-ticket skin for a dark neon-glassmorphism "crazy/genZ" theme (Unbounded + Space Grotesk fonts, animated aurora-blob background, glass cards with animated conic-gradient glow rings, per-tag neon glow, mouse-tracked 3D tilt on every card, confetti burst on done). Kept the same component structure/architecture — this is a full re-skin plus new interaction, not a rewrite.
- Added a two-tap "arm → confirm" interaction for starting/resuming a rail ticket, replacing the old single-click-commits behavior: first tap just "arms" the ticket (glow pulse + a "tap again to start/resume · esc to cancel" badge, auto-expires after 4s), second tap on the same ticket actually starts/resumes it. Fixes a real reported bug: a single accidental tap used to immediately activate a ticket and trap the user in the pause/done/drop flow with no way back. Escape or a click anywhere else cancels the arm with no server call ever made.
- Added an Escape-to-cancel path for a *voluntary* pause (pressing "pause" on the active ticket with nothing else going on) — reverts to active without requiring a note. Escape is disabled during a *forced* pause (triggered by starting/resuming a different ticket while one is active), since that forced transition is the spec's intended behavior, not an accident.
- Added a "← back" button (plus a `b` keyboard shortcut) on the active ticket that actually undoes starting it — a real bug fix: the arm/confirm safety net only stopped *accidental* activation, but once a ticket was genuinely active there was still no way out besides committing to pause/done/drop. New `POST /api/tasks/:id/back` endpoint reverts an active task to `paused` (keeping its existing note, if any) or `queued` (if it never had one), with no note required — distinct from the spec's "pause" action, which still always requires a note.
- Swapped the display font from `Unbounded` to `Bricolage Grotesque` — Unbounded's blocky geometric letterforms read as cheap next to the glass/neon UI; Bricolage Grotesque has more personality and pairs better with Space Grotesk for body text.
- Added 5 switchable color themes (Nebula, Sunset Pop, Matrix, Bubblegum, Mono Ice) via `src/themes.ts` — a full CSS-variable palette per theme, applied by setting them directly on `documentElement.style` and persisted to `localStorage`. A swatch picker (top-right dot) lets the user switch anytime; this replaces relying on `prefers-color-scheme` for light/dark, since the themes include both light (Bubblegum) and dark palettes and the user now has explicit control instead of the OS deciding.
- Added priority handling, explicitly requested after the original spec's "no priorities" rule — resolved as a single binary `urgent` flag rather than a numeric priority scale, since the real need described ("I have to do this right now") is binary, not graduated. Design: urgent tickets (a) always sort before every non-urgent one regardless of age/position, (b) get a persistent red "🔥 do this now" badge, a red/orange glow ring (overriding the tag color), and a continuous subtle pulse — unmissable at a glance, no need to read text to notice it. Deliberately did NOT auto-interrupt the active task when something urgent is added — that would re-break the single-active-task guarantee and the required pause note; the user still chooses when to switch, just with maximum visual pressure to do so.
- Urgent can be set at creation (a toggle in the add form) or toggled anytime on a queued/paused ticket via a small flame button in its corner — separate hit target from the arm/confirm start interaction so toggling urgency never accidentally arms/starts a ticket.
- Backend: `urgent` column added via a runtime migration (`PRAGMA table_info` check + `ALTER TABLE` if missing) rather than a fresh-schema-only column, so it's safe against an already-existing `/data/queue.db` from before this change. `GET /api/tasks` now orders `urgent DESC, position ASC`; a new `PATCH /api/tasks/:id/urgent` toggles it.
- Persistence clarification: data was reported as "empty after refresh" during development. Root cause was never a code bug — `data/queue.db` was repeatedly deleted by the developer's own `rm -rf data` cleanup between manual test passes while iterating on features, each time wiping real accumulated tasks. Verified directly with `sqlite3`/`file` that the on-disk file is a genuine, valid SQLite 3 database and that task rows correctly survive container restarts and rebuilds. Stayed on `sql.js` rather than switching to a native binding (`sqlite3`/`better-sqlite3`) — those require a native binary matching the *container's* OS/arch, built at `npm install` time, and this sandbox's Docker has no network inside the build (see the `sql.js` migration note above); reintroducing a native dependency would bring back that exact failure. Added two concrete, permanent safeguards instead: atomic (temp-file + rename) writes so a crash mid-save can never corrupt the file, and a startup log line reporting how many tasks were loaded from disk, so persistence is trivially verifiable from `docker logs` without guessing.
- Docker: multi-stage build — stage1 builds the Vite frontend, stage2 is slim Node runtime with only server deps + built dist, per spec.
- Environment correction: this sandbox's Docker daemon has no outbound network from build containers (only pre-cached base-image layers resolve; `RUN npm install` inside any Docker stage fails with EAI_AGAIN, confirmed even with explicit proxy env vars). Worked around by building the frontend (`npm run build`) and installing server deps on the host (which does have network) before `docker build`, and having the Dockerfile `COPY` the prebuilt `dist/` and `server/node_modules` instead of running installs inside the container.
- Bug fix (found via real headless-browser testing with Playwright, not just curl): the frontend's `api.ts` always sent `Content-Type: application/json` even on no-body requests (`start`, `resume`, `done`, `drop`). Fastify rejects a JSON content-type header on an empty body with a 400, so every one of those four actions silently failed — only `create`/`pause` (which do send a JSON body) worked. This was the cause of "ticket has no options" / "can't interact with anything": clicking start/resume/done/drop did nothing because the request 400'd before ever reaching the handler. Fixed by only setting the JSON content-type header when a body is actually present.
- Switched the backend from `better-sqlite3` to `sql.js` (pure WASM/JS, no native compilation) specifically because of the above constraint: `better-sqlite3`'s native binding is built for the install-time platform (macOS host) and won't run inside the Linux container, and there's no network inside the container to rebuild/download a Linux binary. `sql.js` has no native parts, so host-installed `node_modules` run unmodified inside the container. The on-disk file is still a real SQLite file at `/data/queue.db`; writes are persisted by re-exporting the whole DB to disk after each mutation (acceptable at this app's write volume).
